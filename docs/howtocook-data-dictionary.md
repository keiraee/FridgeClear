## 2. 菜谱文件结构

除模板外，菜谱普遍包含以下四个二级标题：

```markdown
## 必备原料和工具
## 计算
## 操作
## 附加内容
```

每个菜谱通常还包含：

```markdown
# 菜名的做法

菜谱介绍文本

预估烹饪难度：简单/中等/困难或星级

预估卡路里：数字 大卡

![菜谱图片](./图片文件)
```

## 3. 原始字段字典

| 原始位置 | 内容 | 结构化程度 | 第一阶段处理方式 |
|---|---|---|---|
| 文件路径 | 分类、菜谱目录、文件名 | 高 | 解析分类和源文件路径 |
| 一级标题 | 菜名 | 高 | 去除“的做法”后作为菜名 |
| 标题后的普通段落 | 菜谱介绍 | 中 | 保存为描述文本 |
| `预估烹饪难度` | 难度 | 中 | 保存原文，同时映射简单/中等/困难 |
| `预估卡路里` | 热量 | 中 | 尝试解析数字，无法解析时为空 |
| 图片引用 | 成品图 | 中 | 保存相对路径，不在第一阶段处理图片识别 |
| `必备原料和工具` | 食材、调料、厨具 | 低 | 保存原始行，后续分类为食材或工具 |
| `计算` | 份量和用量 | 低 | 保存原始文本，并尝试解析数量和单位 |
| `操作` | 有序烹饪步骤 | 中 | 按编号保存步骤原文 |
| `附加内容` | 注意事项、参考链接、安全说明 | 低 | 保存原文和链接 |

## 4. 重要数据特征

### 4.1 食材和工具混在同一章节

例如：

```markdown
## 必备原料和工具

- 鸡蛋
- 西红柿
- 食用油
- 炒锅
- 菜刀
```

不能只把这一章节全部作为食材。需要先保留原始条目，再通过默认工具词表或 AI 辅助区分 `INGREDIENT` 和 `TOOL`。

### 4.2 食材名称可能包含别名和可选标记

已发现以下形式：

```text
青蟹（别称：肉蟹）
生粉（别称：淀粉）
青菜（又称上海青）
藤椒油（可选）
```

因此食材至少需要保留：

- 原始名称
- 标准名称
- 别名
- 是否可选

### 4.3 用量不是统一格式

已发现的单位包括：

```text
克、g、千克、kg、毫升、ml、升、斤、个、只、枚、颗、块、片、瓣、根、勺、汤匙、茶匙、包、袋、把、段、张、杯、碗、罐、瓶
```

同时存在：

```text
10g
10 g
10 克
10-15ml
1 个
一根大葱
按个人口味
适量
```

所以第一阶段必须同时保留：

- 原始用量文本
- 可解析的数值
- 单位
- 最小值和最大值
- 是否可计算

### 4.4 `计算` 章节不一定是严格配方表

常见表达包括：

```text
每份够 2 个人吃
按比例调整
以下是两斤食材的量
油 10-15ml
盐适量
```

第一阶段不能假设每个菜谱都能得到精确的标准用量。AI 规划时需要知道哪些用量是可靠的，哪些只能作为参考。

### 4.5 步骤是半结构化文本

步骤通常是有序列表，但内容可能包含：

- 时间
- 温度
- 火候
- 判断标准
- 食材替换说明
- 多个动作

例如：

```text
5. 倒入开水 300ml，焖煮 3 分钟。
```

第一阶段保存完整步骤文本，不强行拆分火候、温度和动作。

### 4.6 图片不是每个菜谱都有

部分菜谱包含相对路径图片，图片通常位于菜谱目录中。第一阶段只保存图片相对路径，不做图片识别和图片上传。

## 5. 第一阶段的标准化边界

### 必须结构化

- 菜名
- 原始分类
- 菜谱文件路径
- 难度
- 卡路里（如果可解析）
- 原始 Markdown 内容
- 原料/工具原始条目
- 原始用量文本
- 步骤顺序和步骤文本

### 可以后续处理

- 食材标准名称
- 食材别名
- 食材和工具分类
- 用量范围
- 单位换算
- 烹饪时间
- 火候
- 食材替代关系
- 营养成分

## 6. 对 FridgeClear 的结论

HowToCook 应该被视为两个层次的数据：

```text
原始 Markdown 文档
    └── 用于 AI 知识检索、菜谱详情和溯源

标准化菜谱数据
    └── 用于库存匹配、过滤、菜单规划和采购清单
```

下一步不是直接写导入器，而是基于本字典设计 FridgeClear 的领域模型和数据库字段。
